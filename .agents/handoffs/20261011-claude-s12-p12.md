## How it was measured (and what that is worth)

- A TEMPORARY, UNCOMMITTED harness page (`src/app/style/p12/page.tsx`, copy kept as `.agents/handoffs/evidence/p12/scripts/harness-page.tsx.txt`) mounts each phone screen inside the real `V3Root` (so the real providers, `.needt-v3` scope, theme, PhoneShell with menu A, PhoneOverlays), phone UI forced. `/style` is a public route, so no session, flag or database is involved. `/api/*` is answered by Playwright from seeded JSON (`scripts/lib.js`, `seed()`); there is no Postgres in the loop (a server binary exists; I did not need it).
- `flock /tmp/build.lock npm run build` then `next start` (production build; the dev server runs React StrictMode and the TanStack devtools button, which distort both the counts and the animations: see "Found in dev" below). Chromium 1194 from `/opt/pw-browsers`, viewport 390x844, deviceScaleFactor 3, `isMobile`, light and dark, `Emulation.setCPUThrottlingRate` 4 for the traces.
- "After" is the same production build with `phone-perf.css` appended to the page at run time (`addStyleTag`), so before and after differ in nothing else. The shipped CSS is the same file the jest test reads.
- Headless Chromium rasterises in software at 3x. Absolute fps from it is NOT a device number and is not offered as pass or fail; only before-versus-after on the same machine, run alternately, is comparable, and the run-to-run spread (shown) is as large as most of the differences. What is NOT measured: a real phone, a real GPU, the Chrome Performance panel's own frame chart (I used the CDP trace's event counts and durations and an rAF frame-time sampler instead), the iOS Safari engine (no WebKit here), real data volumes (the seed has 48 tasks, 5 docs, 3 boards, 4 mails).
- Scripts to repeat all of it: `.agents/handoffs/evidence/p12/scripts/` (`rest.js` per-screen scan and screenshots, `motion.js` mid-motion sampling and traces, `layers.js`, `agg.js`, `recalc.js`, `styletrace.js`). Paths inside are the scratchpad's; change `OUT`/`SHOTS`/`BASE`.

So the acceptance line "no Layout/Paint per frame" holds for every transform-only motion and cannot hold for the three clip-path motions (menu, composer, pull-down) as designed. Layout never runs per frame in any of them.

What costs the menu its frames (4x): about 40-50 % of the main-thread window is style recalculation (`UpdateLayoutTree` 560-810 ms of 1.4-1.8 s), of which one recalc of 157 elements at the first frame is 410-650 ms. Measured by flipping the attributes on a settled page: `inert` on the host 40-70 ms, `data-moving` on `.nva` 34-39 ms, `data-nva-moving` on the host 7-15 ms. Trying to shave it with less `will-change` (rows, shadow pieces, tiles) changed nothing (`UpdateLayoutTree` 670-900 ms either way, raster tasks x4). This is P2's: moving `setInert` to the settle and not promoting 60 layers at the first frame are the two levers; I did not change the menu.

## JS read-through (code, plus the traces above)

Fixed, minimal, owner named:
- P1 `kit/Sheet.tsx`: `paint()` wrote `data-pk-y` on the layer every frame; nothing reads it (grep over `src`): removed.
- P1 `kit/Sheet.tsx` (found by the harness in the dev server): React StrictMode (dev, and the Playwright suite that runs `next dev`) unmounts and remounts a sheet that mounts already open (the composer from the pill). The unmount cleanup cancelled the morph's frame but left `S.open` true, so the remount's layout effect found nothing to start and the composer sat at the pill's clip for good. The cleanup now resets `S.raf`, `m.raf` and `S.open`. Production was never affected (no double mount). New test `kit/__tests__/strictmode.dom.test.ts` mounts the open sheet in StrictMode and checks it morphs and settles; it fails without the fix.

Read and fine: one `frameWriter` rAF per pointer stream (Menu, Sheet, PullDown, the reader slide, lift); no `getBoundingClientRect`/`offsetHeight` in a pointermove or rAF path (rects are read at the lift, in `measure()` on resize and in the Menu's layout effects); springs write through refs; the non-passive `touchmove` of Sheet and PullDown exists only between touchstart and end and is removed on unmount; every `pkTrack` returns its detach; `pointercancel` never commits; no rAF runs at rest (the rest scan shows nothing but the fog drift).

Reported, not changed:
- P1 `PkChips` (`kit/Material.tsx` ~625): the layout effect has no dependency array, so the scroll listener and the ResizeObserver are torn down and rebuilt on every render; the scroll handler sets two data attributes on every scroll event. Harmless, wasteful.
- P1 `PkPullDown.onPlateDown` calls `pkTrack` and drops the returned detach: an unmount in the middle of a plate drag leaves the window listeners until the pointer lifts. They still end on pointerup or cancel.
- P2 `Menu`: `measureLists()` (a layout read, `rows.offsetHeight`) runs in a no-dependency layout effect, so on every render of the Menu (state changes of hint, hold and mode only, never per frame). `setInert` on the host is the single heaviest style flip (above).
- P3 `lift.ts`: while a dragged row is near an edge, each frame reads `scrollTop` right after writing it (a forced layout per frame during autoscroll only).
- Timers at rest, all coarse: `home/clock.ts` and `PhoneHabits` 60 s (a re-render of the screen per minute), `usePkSkyMood` 15 min, `V3Root` 60 s while the Time theme is chosen. No `setInterval` drives a frame.
- `PkScreen` and `ReaderPhone` read `scrollHeight`/`clientHeight` in a passive scroll handler; writes are gated on the clamped values changing, so they happen only in the first 80 px and the last 60 px.

## Context

Reused, not rebuilt:

- **AI path.** `getConfiguredSchedulerAI` + `getPreparedSchedulerAI` (`src/services/ai/settings.ts`). Preparing the hosted client claims one action from the monthly allowance (`claimHostedAiAction`); when the allowance is spent the prepared source is `none`. Own-key (BYOK) is not metered. `releaseHostedAiAction` gives a claim back.
- **Entry and subtasks.** `Task.entry`, `TaskPart`, `SUBTASK_GUIDANCE` and the shared schemas in `src/services/tasks/subtasks.ts`.
- **Undo.** `runOp` writes an `AgentAction` with an inverse in the same transaction; `POST /api/agent/actions/:id/undo` runs it; `GET /api/agent/actions` is the history. Conflict detection compares the `updatedAt` of the `touched` rows.
- **Placement.** `task.spread` over `spreadAcrossDays` / `loadSpreadDays`. The scheduler already treats `postponedUntil` as a not-before date.
- **Notice.** `notify` facade; a server event reaches the open app over the existing realtime stream, the way `focus-ended` does.

## Decisions

1. **Work happens in the worker, not the request.** Creating a task never waits for an AI call. A create enqueues `easy-start-create`; the worker writes the entry. A periodic `easy-start-sweep` handles stuck tasks and overloaded days, and `easy-start-backfill` (every 3 hours) gives existing tasks an entry. Redis not configured: nothing runs (same as every other queue).
2. **One op for the rewrite: `task.simplify`.** It sets `entry`, optionally `title`, and appends subtasks, in one transaction. It re-reads the task inside the transaction and refuses (CONFLICT) when a create or backfill finds an entry already there, or when the task no longer matches what the plan was made from (`expected`: title, entry, `simplifiedAt`). Its inverse is `task.restore` with the old `title`/`entry` and `removePartIds`, plus `startCooldown`: undo sets `simplifiedAt` to the undo time and `rescheduleCount` to 0, so the sweep and the backfill never redo a first step the person took back. The added subtasks are `touched` rows, so undo refuses (409) when the person ticked, renamed or deleted one.
3. **Reschedule counter.** `Task.rescheduleCount` is incremented when a task is given a LATER calendar day in the person's zone, by anyone: `task.update`, `task.move_to_day`, `PUT /api/tasks/:id` and the scheduler. Earlier days, same-day time changes and a first placement do not count (`src/services/easy-start/moves.ts`, pure). A move made by easy start's own spread does not count. The feature no longer writes `previousScheduledStart`.
4. **Stuck rule.** Open (`todo`), not someday, not recurring or habit, no done subtask, and either `rescheduleCount >= 1` or its start (`startDate`, else `scheduledStart`) is 2 or more days in the past and nothing touched it since. After a rewrite `simplifiedAt` is set and `rescheduleCount` reset; no new rewrite for 7 days. An undone rewrite is therefore not redone. The thresholds are constants in `rules.ts`, not settings.
5. **Sweep progress.** A task the sweep examines and does not rewrite is stamped (`simplifiedAt`), so it leaves the candidate set and later pages are reached. The candidate query mirrors the rule (done subtasks, cooldown, start cut-off), pages by id cursor, and the crowded-day scan rotates through all accounts with a worker-memory cursor. A task skipped for a cap is not stamped.
6. **Overload rule.** Per editable workspace, count open tasks per local day (`taskDayInZone`). Above 6, the lowest-priority ones beyond the 6th that are auto-scheduled and not pinned, locked, frozen, hard-deadline, habit, series, synced or in an excluded project go to `task.spread` with `afterDay` (later days only) and `notBefore` (hold the task on its new day through `postponedUntil`; never invent a `dueDate`). If the person undid an automatic spread in the last 24 hours, that person is skipped.
7. **Modes.** `easyStartMode` is a typed column (the worker reads it). `auto` changes tasks. `suggest` stores an `EasyStartProposal` (with the title and entry it was made from) and announces "Simplify?"; Apply runs the same `task.simplify` as the person and a proposal whose base changed is stale. Overload spreading and the backfill are `auto` only. `easyStartExcludedProjectIds` is a typed array column.
8. **Fallback and plans.** `fallbackPlan()` returns "Open it and do the first 10 minutes." with no subtasks. It is used when AI is unavailable, out of quota, in the slow lane, unreadable, or the account is Free without its own key (nothing claimed). Free with BYOK gets the AI step on its key. A hosted claim that ends as a fallback or a failed write is released. A create-time fallback is still recorded as a `task.simplify` action, so it can be undone.
9. **Kill switch.** Flag `always_easy_start`. A data migration turns it on at 100%; no gradual rollout. Every entry point checks flag and setting and returns without side effects when either is off; a failed settings read is treated as off.

## Risks

- A wrong rewrite of a title. Mitigation: undo, 7-day cooldown, only stuck tasks, suggest mode.
- AI cost. Mitigation: metered through the existing claim; per-run caps in the sweep and a 25-per-person batch in the backfill; the backfill spends at most 10 hosted AI actions per person per day (counted from today's `task.simplify` backfill actions) and leaves the rest for the next day, never writing the fixed entry in their place; a background job never waits in the slow lane (over the allowance it takes the fallback); a task with a pending suggestion is not a sweep candidate and the sweep scan keeps its place across runs; Apply re-checks the task is still open work; claims released when unused.
- Worker-memory cursors reset on restart. Mitigation: a restart only means the scan starts again from the first account.
